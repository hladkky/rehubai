## 1. Питання і теза

Валідатор оцінює геометричну коректність пози через **відносні кути між трійками
опорних точок** (θ = arccos(u·v / (‖u‖‖v‖)), `rehubai/angles.py`). Постає
питання: чи достатньо для цього **двовимірних** координат (x, y) з відеокадру, чи
потрібні **тривимірні** (x, y, z)?

**Теза:** для реабілітаційних вправ, де кінцівка рухається у напрямку до/від
камери (лежачи, сагітальні рухи, косий ракурс), обчислення кута лише за (x, y)
дає **систематично завищені** значення — суглоб виглядає «розігнутим», хоча
насправді зігнутий у глибину. Тому система має споживати 3D-координати, причому
саме **метричні world-landmarks**, а не пікселі з проєкції.

## 2. Метод перевірки

- **Детектор:** MediaPipe Pose (BlazePose, 33 точки), `model_complexity=2`,
  `static_image_mode=True`, `min_detection_confidence=0.5`.
- **Дані:** три фази вправи «dead bug» (`artifacts/assets/dead_bug/phase_{0,1,3}.png`,
  1280×720) — людина лежить на спині, **вид збоку**. У цьому ракурсі ліва і права
  кінцівки збігаються в площині кадру, але рознесені по осі глибини z.
- **Величини:** для кожного знімка обчислено кут у лікті (плече–лікоть–зап'ясток)
  двома способами — за (x, y) і за (x, y, z) — на **world-landmarks** (метри,
  початок координат у центрі таза). Порівняно також normalized- та
  world-представлення і значення `visibility` для ближніх/дальніх суглобів.

## 3. Результати

### 3.1 MediaPipe справді віддає z

Обидва набори точок містять третю координату:
- **normalized:** `x, y ∈ [0, 1]`, `z` — оцінка глибини в тому ж масштабі, що x
  (менше z = ближче до камери), відлік від таза;
- **world:** метричні `x, y, z` у **метрах**, початок — середина між кульшовими
  суглобами.

### 3.2 z коректно розділяє ліві/праві кінцівки за глибиною

Для phase_0 (world, метри) знак z протилежний для симетричних суглобів — детектор
правильно ставить ближню/дальню кінцівку на різну глибину:

| Суглоб | z (ліворуч) | z (праворуч) |
|---|---|---|
| лікоть | −0.279 | +0.226 |
| коліно | −0.138 | +0.094 |

### 3.3 Кут у 2D vs 3D — розбіжність до 42°

| Знімок | Лікоть | 2D (без z) | 3D (з z) | Δ |
|---|---|---:|---:|---:|
| phase_0 | лівий | 173.0° | 130.9° | **42.1°** |
| phase_0 | правий | 156.1° | 148.0° | 8.1° |
| phase_1 | лівий | 156.8° | 135.0° | 21.8° |
| phase_1 | правий | 158.5° | 150.6° | 8.0° |
| phase_3 | лівий | 174.3° | 133.0° | **41.3°** |
| phase_3 | правий | 169.0° | 149.0° | 20.0° |

У 2D лівий лікоть виглядає **майже прямим (173–174°)**, тоді як у 3D він зігнутий
до **131–133°**. Двовимірна оцінка «губить» згин у глибину на ~40°.

### 3.4 Надійність z корелює з видимістю

z — це **навчена оцінка**, а не виміряна глибина, і її якість спадає для
затулених суглобів (phase_0, `visibility`):

| Суглоб | ближній (до камери) | дальній (за тілом) |
|---|---|---|
| лікоть | 0.99 | 0.12 |
| коліно | 0.97 | 0.22 |

## 4. Аналіз

1. **2D недостатньо.** Розбіжність до 42° (§3.3) перевищує будь-який розумний
   допуск ε кутового обмеження. Система на самих (x, y) **не зафіксувала б**
   помилку згину руки у вправах лежачи чи в сагітальних рухах при фронтальній
   камері — це хибнонегативний результат, неприйнятний для реабілітації.
2. **World, а не normalized.** Normalized-z прив'язаний до масштабу кадру
   (проєкція), тоді як world-landmarks — метричні й центровані на тазі, що дає
   інваріантні до ракурсу й антропометрії кути (ключова теза новизни). Normalized
   годиться лише для піксельних перевірок положення (y_above/y_below).
3. **z ≈ f(visibility).** Оскільки глибина дальніх суглобів «домальовується»
   (§3.4), сліпо довіряти їй не можна — потрібне зважування на `visibility`.

## 5. Рішення, ухвалене в системі

- **Бекенд повертає world-landmarks** у режимі `use_world_landmarks=True`
  (`MediaPipePoseBackend`), тобто метричний 3D-скелет для кутових перевірок;
  піксельний режим лишено для конфігів із позиційними перевірками.
- **Confidence-gating.** `visibility` передається у валідатор як довіра до точки;
  `confidence_ok` (`rehubai/angles.py`) пропускає кутову перевірку, якщо
  задіяний суглоб має низьку видимість → менше хибних порушень на затулених
  (дальніх) кінцівках. Це закриває ідею №2 плану.
- **Узгодженість трактів.** UI-PRMD-скелет після прямої кінематики
  (`rehubai/datasets/uiprmd.py`) теж дає **абсолютні 3D-точки**; MediaPipe у
  world-режимі — також 3D. Обидва входи потрапляють у валідатор в одному
  представленні → кути рахуються однаково, один конфіг валідує обидва джерела.

## 6. Відтворюваність

MediaPipe 0.10.21, Python 3.9.13, `model_complexity=2`, `static_image_mode=True`.
Числа з §3 отримано так:

```python
import cv2, numpy as np
from rehubai.backends.mediapipe_backend import MediaPipePoseBackend
from rehubai.angles import calculate_angle
from rehubai import joints

be = MediaPipePoseBackend(use_world_landmarks=True, static_image_mode=True)
kps, conf = be.detect(cv2.imread("artifacts/assets/dead_bug/phase_0.png"))
i = lambda n: joints.resolve("blazepose33", n)
s, e, w = kps[i("left_shoulder")], kps[i("left_elbow")], kps[i("left_wrist")]
print("3D:", calculate_angle(s, e, w), " 2D:", calculate_angle(s[:2], e[:2], w[:2]))
```

Регресійні тести: `tests/test_mediapipe_backend.py` (world-режим повертає
метричні координати; 3D-кут відрізняється від 2D для затуленого в глибину ліктя).
Прогін відео у 3D: `python -m rehubai.eval.run_video ... --world`.

## 7. Наслідки для методики зйомки власних відео

- Ставити **робочу кінцівку до камери** (у dead bug ближня рука має
  `visibility` 0.99, дальня — 0.12); дальні суглоби мають ненадійний z.
- Обирати ракурс під мінімум оклюзій (фронт для рухів у фронтальній площині, бік
  — для сагітальних), а не «підганяти» під UI-PRMD (там відео немає — це скелет).
- Для перевірки заявленої інваріантності знімати кілька повторів під ±10/20/30°.

## 8. Обмеження

- Монокулярний 3D — це оцінка, а не вимір; для суто глибинних рухів (ротація
  плеча, m09) точність z обмежена навіть при добрій видимості.
- Числа §3 отримані на трьох статичних кадрах одного суб'єкта — вони **ілюструють
  ефект**, а не є статистикою; кількісна оцінка 2D vs 3D на вибірці — задача
  експериментального розділу (харнес метрик, Місяць 3).
